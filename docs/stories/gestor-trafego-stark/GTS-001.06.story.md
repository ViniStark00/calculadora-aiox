# GTS-001.06 — Tasks, Workflows, Checklists e Templates

## User Story

**Como** stark-chief recebendo um comando do gestor,
**quero** tasks que descrevem exatamente o fluxo de execução de cada rotina,
**para que** o pipeline `*rotina-semanal` execute as 6 fases na ordem correta,
reutilizando dados coletados na FASE 1 sem buscar a API duas vezes.

---

## Contexto

Este é o conjunto de arquivos mais crítico da implementação. A `tasks/rotina-semanal.md`
orquestra todos os agentes e é onde o reuso de dados entre fases é implementado.

**Restrição crítica (DESIGN.md ADR-04):** A FASE 1 (alerta-monitor) coleta métricas Meta Ads
e disponibiliza `metricas_coletadas`. A FASE 2 (coletor/sheets) DEVE reutilizar esses dados
para métricas Meta Ads — chamadas adicionais à API para as mesmas métricas são proibidas.

Todos os arquivos escritos do zero.

## Critérios de Aceite

### tasks/rotina-semanal.md (CRÍTICO)

**Estrutura de 6 fases (ordem obrigatória):**

- [ ] **FASE 1 — MONITORAMENTO** está presente como primeira fase
  - Aciona `@alerta-monitor`
  - Aciona `@validator → gate_alertas`
  - Output explícito: `alertas_ativos` + `metricas_coletadas`
  - Comportamento de FAIL: exibe alertas + pergunta se quer continuar

- [ ] **FASE 2 — PLANILHA SHEETS** está presente como segunda fase
  - Condição explícita: `vinicius in cliente.gestores` → executa FASE 2; caso contrário, pula
  - Passa `metricas_coletadas` da FASE 1 como parâmetro para `@coletor`
  - Menciona explicitamente: "coletor NÃO busca Meta Ads novamente — reutiliza metricas_coletadas"
  - Coletor ainda busca Google Ads e seguidores via Reportei
  - Aciona `@validator → gate_sheets`
  - Comportamento de FAIL: para e reporta problemas

- [ ] **FASE 3 — NARRATIVA** está presente como terceira fase
  - Aciona `@contexto-cliente (LEITURA)` — não-bloqueante
  - Aciona `@redator` com métricas completas (Meta + Google + seguidores)
  - Aciona `@validator → gate_reportei`
  - FAIL 1ª vez: retorna ao redator para regenerar
  - FAIL 2ª vez: interrompe e informa

- [ ] **FASE 4 — PUBLICAÇÃO** está presente como quarta fase
  - Aciona `@publicador → create_timeline_event`
  - Aciona `@whatsapp-writer`
  - Fases 4 e 5 são acionadas EM PARALELO (documentado explicitamente)

- [ ] **FASE 5 — STATUS REPORT CLICKUP** está presente como quinta fase
  - Aciona `@clickup-writer → draft → aprovação → escreve`
  - Aciona `@validator → gate_clickup`
  - Executada em paralelo com FASE 4

- [ ] **FASE 6 — WRAP-UP** está presente como sexta e última fase
  - Aciona `@coletor → save-history` (não-bloqueante)
  - Aciona `@contexto-cliente ATUALIZAÇÃO` (não-bloqueante)
  - Aciona `@task-monitor → marca tarefas` (não-bloqueante)
  - Falhas na FASE 6 geram aviso no resumo — não bloqueiam

**Ordem de criação sugerida:**
1. Criar checklists e templates primeiro (sem dependências)
2. Criar tasks simples (fetch-metrics, verify-fill, generate-report, etc.)
3. Criar rotina-diaria.md
4. Criar rotina-semanal.md por último (depende de saber o que os outros fazem)

**Comportamento de falha de fase (DESIGN.md seção 3.4):**
| Fase | Falha | Comportamento |
|------|-------|---------------|
| 1 MCP indisponível | Continuar sem metricas_coletadas; FASE 2 busca tudo do zero |
| 1 gate FAIL | Exibir alertas + perguntar se quer continuar |
| 2 gate FAIL | Parar; não avançar sem confirmação |
| 3 gate FAIL (2x) | Parar; aguardar ação |
| 4 MCP indisponível | Marcar FASE 4 como SKIPPED; continuar FASE 5 |
| 5 MCP indisponível | Marcar FASE 5 como SKIPPED; continuar FASE 6 |
| 6 qualquer falha | Aviso no resumo; nunca bloquear |
